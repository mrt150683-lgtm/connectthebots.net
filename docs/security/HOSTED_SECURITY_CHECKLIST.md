## Field-to-payload matrix

Enum, count, date, token and identifier inputs are not treated as HTML; rejection/no mutation is the expected result.

## Query construction review

The review enumerated `execute`/`executemany` call sites in every hosted Python module and traced nonliteral query components. No user value is interpolated into SQL syntax. The relevant trusted assembly is:

| Modules | Dynamic syntax source | Request values |
| --- | --- | --- |
| `auth.py`, `sessions.py`, `account_data.py`, `report_store.py`, `operator_alerts.py`, `lifecycle.py` | Fixed statements | Identity, tokens' hashes, profile, report metadata, preferences and timestamps supplied as parameters |
| `board.py` | Fixed `_APPROVED`/`_VISIBLE` clauses and fixed viewer filter; fixed ORDER/LIMIT syntax | Owner, slug, search pattern, limit/offset bound; search wildcard escaping is separate from SQL syntax |
| `interactions.py` | `_approved` selects only `p.user_id` or `p.slug`; list sections use internal fixed predicates; message cursor adds a fixed predicate; erasure loops only `introductions` and `conversations` | All owners, targets, messages, cursors, hashes and paging values bound |
| `notifications.py` | Column names only from constant `KINDS`, including after token validation; `_visible_sql()` embeds only fixed board SQL | Owner IDs, kinds used as values, times and paging values bound |
| `moderation.py`, `operator.py` | Fixed approved-posting projection and visibility clauses | Reporter/subject, target IDs, details, dates and paging values bound |
| `db.py`, `recovery.py` | Packaged/checksummed migrations, fixed PRAGMA/schema checks and fixed restoration statements | Schema SQL is trusted code, never a request payload; data copying uses bound values |

Changing a query allowlist or introducing a new request-driven SQL fragment requires a fresh review. This is a written check, not a static analyzer guaranteeing future edits are safe.

## Credential storage and comparisons

| Credential or value | Storage/check | Limitation |
| --- | --- | --- |
| Session token, report bearer key | Random 256-bit secret, hash-index lookup plus `hmac.compare_digest` of fixed digest; current owner/revocation/expiry checked | A stolen valid token remains a capability until expiry/revocation. SQLite lookup timing is not constant-time. |
| OAuth state/browser binding/nonce | Hashes retained; fixed-format validation then `compare_digest`; single-use attempt removed before exchange | PKCE verifier is deliberately temporary server-side plaintext needed for the code exchange; no Google access/refresh token is retained. Provider RSA signature validation uses the pinned library. |
| CSRF, preauth cookie/CSRF | Purpose-specific HMAC with fixed-format validation and `compare_digest` | Browser same-origin compromise can exercise the user's legitimate authority. |
| Paste/prompt/publication/introduction/message/moderation previews | Owner/purpose/expiry-bound HMAC checked with `compare_digest`; current service authority rechecked | Encoded preview content is signed, not encrypted; it is visible in that person's browser. |
| Account/operator unsubscribe | Distinct purposes/namespaces; HMAC `compare_digest`; current opaque handle and kind/recipient lookup | Anyone possessing a valid link may disable that email type. No account read access is granted. |
| Invite and waitlist removal code | Only cryptographic hash is stored; database lookup by complete digest, never plaintext or prefix equality | No application raw-secret comparison exists here. Do not describe hash-index SQL lookup, response timing or the whole service as constant-time. |
| Backup encryption, restore-secret fingerprint, integrity hashes | AES-GCM authentication by pinned cryptography; restore fingerprint/digest uses `compare_digest` | Database and process administrator remain trusted. Nonsecret owner IDs, statuses, expiry times, schema checksums and recipient-binding hashes use ordinary comparisons. |

The written review checks explicit secret-comparison code; it is not a statistical timing proof. Source includes no constant-time claim for database access, network transport or missing-versus-valid account branches.

## Erasure and recovery safeguards

These privacy boundaries extend the brief's shorter checklist:

- `test_auth.AuthErasureRaceTests.test_inflight_verified_callback_cannot_recreate_erased_account_but_fresh_login_can`, `test_erasure_invalidates_unconsumed_attempt_without_identity_tombstone`, and `test_final_callback_rechecks_recovery_hold_before_session_writes` cover erasure/recovery during real signed-token verification. The browser moderation journey also pauses its fictional provider exchange, deletes through the actual CLI, then releases it.
- `test_recovery.RecoveryAuthorityTests.test_later_suspended_identity_cannot_signup_after_recovery_release`, `test_later_block_survives_both_accounts_reviewed_and_fresh_publication`, and `test_snapshot_identity_missing_or_conflicting_in_live_authority_refused_atomically` preserve trusted current identities/profiles and blocks instead of letting an old snapshot undo newer choices.
- `test_recovery.EncryptedRecoveryTests.test_account_and_waitlist_erasure_refuse_older_backup_without_mutation`, `test_fresh_host_foreign_lineage_and_missing_target_cannot_claim_authority`, and `test_active_runtime_lock_refuses_restore_but_allows_backup` cover stale authority and running-process conflicts. Actual CLI source/installed-wheel restore evidence complements unit tests.

Restore still requires an intact trusted current database with matching lineage/erasure generation and quarantines every account. Losing that authority cannot currently be repaired from offsite backups alone. Independent current-authority custody, off-server storage/key custody and a fresh-host disaster-recovery procedure remain launch work.

## What local evidence does not prove

Local identity fixtures prove protocol and user-flow boundaries without contacting Google. Outbox/fake SMTP tests prove queued decisions and transport contracts without real delivery. Installed staging uses local HTTP with sign-in disabled; it does not prove public HTTPS, provider callbacks, mailbox usability, certificate alerts or production retention. Final approval additionally needs real-provider staging, accurate approved trust pages, monitored offsite operations, review/green main CI and written approval for the specific production deployment, followed by production smoke checks. No personal name or fabricated company is supplied by this checklist.
