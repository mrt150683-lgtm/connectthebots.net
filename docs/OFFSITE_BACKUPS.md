## Why copying a backup is insufficient

An old database can contain an erased account or omit a later block or suspension. Its own saved watermark cannot prove those changes never happened. The existing local restore therefore requires the intact current database. The new path records a separate, identity-free recovery generation in Backblaze B2 before committing any account creation, identity/profile change, suspension change, block change, account erasure or waitlist removal. It does not change the meaning of the existing erasure generation.

Database triggers mark protected changes. The shared transaction boundary holds `BEGIN IMMEDIATE`, verifies the current remote chain, appends and reads back one authenticated marker, and only then commits the local mutation and generation. A failed or uncertain remote write rolls back the local mutation. It never rolls back remote authority or retries an uncertain write with a new marker. A process death after the remote write but before local commit deliberately leaves a mismatch requiring investigation; there is no “trust this older local database” reset command. Ordinary login timestamp refreshes do not advance authority. The pending growth-safety candidate additionally protects changes/removal of interview, consent, profile-sharing, topic-content and related personal records; it increases protected traffic and does not change the request budget below.

Growth privacy updates/deletions and explicit political consent decisions are
also protected. Migration cleanup uses this same guard on an enrolled database.
Routine check-ins and ordinary content creation do not add markers, but erased
topic signals and changed privacy choices do; budget those requests as well as
scheduled backups. See the [exact mutation, quarantine and migration contract](GROWTH_PRIVACY_RECOVERY.md).

Protected browser transactions execute in worker threads, including their complete SQLite connection lifetime. When independent authority is configured, other writers fail promptly on contention with a safe 503 and `Retry-After`, instead of blocking the sole web event loop while storage responds. A user may need to retry a write during another protected change. This is a single-writer design, not concurrent write throughput; health/read requests remain responsive.

Markers form a complete HMAC-authenticated chain in `authority/`, using a key derived separately from the retained backup encryption key. No names, email addresses, account IDs or message/report contents enter this chain. All versions are listed; duplicates, forks, gaps, hidden entries, malformed signatures and different lineages are refused. Metadata authenticates the complete chain efficiently, and the newest object is downloaded independently. No mutable latest-pointer object establishes authority. The bound is 100,000 markers; review capacity before reaching it.

This assumes one active host, trustworthy storage-account administration, accurate provider reads and no deletion of authority history. It is not protection against a compromised privileged B2 account administrator who deletes history and changes policy back. The application key cannot delete files or administer the bucket. Every provider operation verifies the bucket remains private and refuses lifecycle rules outside the configured `snapshots/` prefix. Never expire, hide, rename or delete `authority/` objects. Replacement-host recovery requires the old host to be stopped and its storage key revoked first.

## Private setup

Backblaze currently offers the first 10 GB free without requiring a payment card. Review the current account terms, region and limits before enrollment. This is a starting allowance, not a guarantee of indefinite free use. [Pricing](https://www.backblaze.com/cloud-storage/pricing), [signup](https://www.backblaze.com/sign-up/cloud-storage).

1. Create a dedicated private bucket in the chosen region. Use a random object prefix `ctb-<32 lowercase random hex characters>/`; never put a person, email address or customer identifier in a bucket or object name.
2. Set retention only for that prefix's `snapshots/` directory. A rule hiding snapshots after 13 days and deleting hidden versions after one further day targets a 14-day retention window; provider processing can extend physical deletion beyond that window. Do not promise an exact maximum without verifying the provider's timing. No rule may cover the whole bucket, whole application prefix or `authority/`. Do not enable replication into this prefix. The application never prunes remote authority history.
3. Create a bucket-and-prefix-restricted key with exactly `listBuckets`, `listFiles`, `readFiles`, `writeFiles`. Do not use the master key or grant deletion/bucket administration. Store it only in the root-owned protected environment, never chat/Git/logs.
4. Preserve `BACKUP_ENCRYPTION_KEY` separately from the VPS and B2 account. A provider copy without this key cannot be decrypted; a key held only on the lost VPS is not recoverable. Keep the chosen bucket/prefix and recovery procedure with that private custody record.
5. Configure all four blank variables in `site/deploy/app.env.example`: `OFFSITE_B2_KEY_ID`, `OFFSITE_B2_APPLICATION_KEY`, `OFFSITE_B2_BUCKET_ID`, `OFFSITE_B2_PREFIX`. Stop app/workers, run the installed admin `recovery enroll` once, then `recovery status` and `backup`. Enrollment refuses a previously enrolled database or nonempty authority prefix. Restart with the same protected settings.
6. Confirm `backup` reports `offsite_verified: true`. Only the completed encrypted `.ctb` file is uploaded; it is downloaded and its SHA-256 compared. No plaintext SQLite scratch file is uploaded. Each snapshot is limited to 128 MiB in this first implementation; increasing that limit needs a reviewed streaming change. Set `OFFSITE_BACKUP_NOTICE` to the reviewed provider, region, retention and transfer details before approving legal pages; approved offsite configuration without this notice is refused. The notice is displayed as escaped plain text, and configuring storage does not itself approve it.

The backup unit has no network access by default (`PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`). After all four offsite variables validate, the installer writes only `/etc/systemd/system/connectthebots-backup.service.d/40-ctb-offsite-network.conf`, enabling the host network and IPv4/IPv6 sockets needed by the verified HTTPS adapter. Filesystem confinement and service identity stay unchanged. When changing an existing installation's protected settings, rerun the reviewed installer or its `configure_app.py` with the current target arguments and `--backup-network-drop-in` pointing to that exact file, then run `systemctl daemon-reload` before the backup worker. Clearing all four variables and repeating this step removes only the managed override and restores network isolation; partial settings, symlinks and an operator-modified override are refused. Never remove configuration from an enrolled host as a workaround for a recovery mismatch.

Credentials must be supplied privately. The CLI returns fixed safe errors without provider response bodies, object capability tokens or secrets. The native adapter uses verified HTTPS, disables environment proxies and redirects, and does not retry uncertain writes. It adds no dependency beyond the existing `httpx` extra. [B2 authorization](https://www.backblaze.com/apidocs/b2-authorize-account), [bucket policy](https://www.backblaze.com/apidocs/b2-list-buckets), [version listings](https://www.backblaze.com/apidocs/b2-list-file-versions), [upload](https://www.backblaze.com/apidocs/b2-upload-file).

## Recovery and availability

An enrolled snapshot is eligible only when its lineage, recovery generation and marker exactly match freshly fetched independent authority. **Every protected change invalidates all older snapshots until a new backup completes.** The default timer is nightly; the optional success monitor below uses an hourly schedule. Run `backup` after a protected change when recovery availability is required, within the account's remaining request budget. Uploading an old file again cannot make it current. A storage outage prevents protected changes; an ambiguous remote/local commit can intentionally leave no recoverable snapshot. `/healthz` checks local application/database health and the local recovery hold; it does not contact B2 or claim that offsite authority is reachable. `recovery status` performs the explicit remote check and exits nonzero on failure. Local health alone cannot cover failed or overdue backups.

## Independent backup-success monitor

The optional `BACKUP_HEARTBEAT_URL` is a private HetrixTools capability, held only in the protected `app.env`. It is omitted from settings representations and CLI output. Only the exact HTTPS host `sm.hetrixtools.net`, path `/hb/`, and one `s` token of 16–256 ASCII letters, digits, underscores or hyphens are accepted. Extra query parameters, fragments, credentials, ports and redirects are refused. The transport sends one verified TLS `HEAD` request, with no body, environment proxy or automatic retry, and accepts only HTTP 200. Response bodies and exception request details never enter operator output. See the official [monitor setup](https://docs.hetrixtools.com/add-a-cron-job-monitor-heartbeat-monitor/) and [HEAD usage](https://docs.hetrixtools.com/how-to-use-the-cron-job-monitor/).

The `admin backup` command signals success only after encrypted upload and digest-checked read-back. Immediately before the signal, it compares that uploaded snapshot's exact lineage, generation and marker against both current SQLite state and freshly fetched remote authority. An actual SQLite writer transaction holds this check through the HEAD request; the separate runtime lock prevents database replacement. Competing writes may receive a retryable 503 while the remote authority check and request complete; WAL reads and health remain available. The HEAD runs in a child process with a seven-second whole-operation timeout, including DNS, TLS and headers, in addition to its five-second socket timeout. Its URL passes only through private stdin, its environment excludes application credentials, and its output is discarded. Timeout kills and reaps that child before the writer fence is released. The existing B2 authority check has its separate network bounds. A failed monitor request makes the command exit nonzero even though the verified backup remains saved. It never retries or prints the private URL.

1. Prepare a private HetrixTools Cron Job/Heartbeat monitor with a **60-minute interval plus five-minute grace (65 minutes total)**, using the approved operator contact list. This is the approved normal policy for the current deployment; the checkpoint above records any temporary attended rehearsal. Obtain approval before other provider changes. Keep it paused or otherwise unarmed until the first real verified backup; do not manually visit its private URL as a test of backup success.
2. Privately add its URL as `BACKUP_HEARTBEAT_URL` alongside the complete B2 settings. Stop the backup timer while updating configuration. Rerun the reviewed installer, or validated `configure_app.py` with the existing environment/target arguments and both `--backup-network-drop-in /etc/systemd/system/connectthebots-backup.service.d/40-ctb-offsite-network.conf` and `--backup-timer-drop-in /etc/systemd/system/connectthebots-backup.timer.d/40-ctb-heartbeat-schedule.conf`. Run `systemctl daemon-reload` and restart the backup timer after validation.
3. The exact owned timer override replaces the nightly calendar with **hourly** backups, removes the five-minute random delay and uses one-second scheduling accuracy. It contains no credentials. Both complete B2 configuration and a valid heartbeat URL are required. The installer atomically upgrades the exact previously shipped quarter-hour override at the same path; it refuses operator changes, any other content and symlinks. Clearing only the heartbeat URL and reapplying the helper removes either recognized managed version and restores the nightly default. Keep B2 configuration on an enrolled host. Verify the effective systemd calendar before restarting the timer. Previously prepared release plans/bundles containing the quarter-hour installer need a new reviewed release plan; do not activate their monitored schedule.
4. Run one real `admin backup` and confirm `offsite_verified: true` and `heartbeat_sent: true`, then confirm the monitor records it. Arm its alerts. In an attended operations window, pause only the backup timer long enough to exceed the timeout while the app and other workers remain available. This rehearsal does not require an hour of website maintenance. Confirm the external alert reaches the operator, restart the timer and run a genuine fresh verified backup to confirm recovery. Record both receipts. The public health monitor remains separate.

The heartbeat proves the **last confirmed point**, not continuous recoverability or zero data loss. A protected mutation immediately after it can invalidate that snapshot until the next backup. With hourly scheduling that gap can approach an hour plus backup duration, and failures can extend it indefinitely. A host loss in that gap may leave no eligible snapshot and must not be bypassed. A 65-minute missed-heartbeat alert means no recent verified backup; a slow job can also cause it. Monitor configuration, provider outages and operator response affect alert delivery. The attended live missed-signal/recovery check passed using the temporary six-minute threshold; the normal 65-minute configuration was restored and verified without waiting through that full interval. The required staging restore remains a launch gate; a replacement-host drill is optional.

## Free-account request and storage budget

The observed initial account caps are **2,500 Class C requests/day, 2,500 Class B requests/day, 1 GB downloaded/day and 10 GB stored**, with zero-dollar spending caps. The account requires payment details to edit those caps; the owner chose no payment details. Public transaction pricing describes the classes as free, but the API separately documents transaction-cap refusal for non-paying accounts. Treat the actual account's caps as authoritative; zero price does not mean unlimited requests. [Transaction classes](https://www.backblaze.com/cloud-storage/transaction-pricing), [non-paying account caps and pagination](https://www.backblaze.com/apidocs/b2-list-file-versions).

For an enrolled backup followed by its heartbeat, let `P` be the number of 1,000-record pages returned when listing the complete authority history. At stable history size, one successful cycle uses **`24 + 5P` Class C and 6 Class B requests**: five fresh authority checks, one encrypted upload and one snapshot read-back. Fresh authorization, exact scope, bucket policy and current authority checks remain intact; this change adds no caching. At `P=1`, the former 96/day schedule needed **2,784 Class C/day before users or manual checks**, exceeding the observed cap. The hourly schedule uses **696 Class C and 144 Class B/day**, leaving **1,804 Class C and 2,356 Class B** for all other activity in the account, before retries, manual backups, status checks and administrative work.

Protected commits consume additional requests and grow history permanently. One protected transaction costs `10 + P_before + P_after` Class C and 2 Class B requests, or `10 + 2P` when its page count is unchanged. A standalone `recovery status` costs `4 + P` Class C and 1 Class B request. At one page, the remaining Class C headroom could cover at most 150 such transactions if absolutely nothing else used it, so this is not a promise of 150 signups or support for 500 users. Monitor actual daily totals and reserve headroom for operations. Each additional history page adds 120 Class C/day to scheduled hourly backups. At `P=16`, scheduled work alone costs 2,496/day; at `P=17`, it exceeds the cap. Review well before those limits. Increasing the listing page size does not bypass billed 1,000-record transaction units, and authority history must not be expired to save requests. [Listing transaction accounting](https://www.backblaze.com/apidocs/b2-list-file-versions).

If a cap is exhausted, the provider can refuse requests. Protected mutations and fresh recovery verification then fail closed; never skip verification to keep writes running. Exhaustion after a marker upload but before its verification/local commit can leave remote authority ahead of the rolled-back local database. A daily quota reset does not repair that mismatch. Stop and investigate the uncertain operation; do not blindly retry it, reset authority or delete history. The hourly schedule reduces the initial baseline, but does not guarantee free operation as activity/history grows. Recheck request totals and physical storage before launch, during early usage and well before either cap; the owner's later 500-user review preference does not override these limits. The account cap alerts are enabled, but their delivery has not been proved by the health-monitor test. The backup overdue/recovery receipts and final monitor-policy restoration are tracked in the current checkpoint.

Snapshot read-back alone downloads **24 times the encrypted snapshot size per day**, before authority-marker reads, manual checks, recovery drills and other account usage. The observed 1 GB/day download cap allows roughly **41.7 MB per snapshot before any reserve**; use actual daily totals, not this theoretical ceiling, when deciding whether the account remains viable.

Hourly scheduling produces 24 snapshots/day, or **336 snapshots across a nominal 14-day window**. The first 10 GB allows roughly **29.8 MB per average snapshot before metadata, authority history, other usage, manual snapshots and lifecycle processing delays**. At 423 KB each, that nominal snapshot set is about 0.14 GB. At the application's 128 MiB per-file ceiling it would be about 45 GB, so that ceiling is not a free-storage budget. Snapshot-only retention is necessary; delayed physical deletion can exceed the nominal window. Review actual stored bytes well before 10 GB. This change adds no paid plan or payment details.

It preserves current local identities and blocks, checks remote authority when enrolled, and creates an encrypted target checkpoint. For complete host loss:

2. Install the exact reviewed application/schema and restore protected configuration and the separately retained encryption key. Create the service-owned target directory but **do not start/migrate a new database**. The target DB, WAL and SHM must be absent.
3. Obtain the completed encrypted snapshot privately from B2. Run `restore --from ABSOLUTE_BACKUP_PATH --lost-host --old-host-fenced`. The flag records the operator's fencing assertion; it cannot itself verify an old host is stopped. No supplied local manifest or stale watermark can bypass the fresh provider check.
4. Inspect the quarantined result. Rotate `SESSION_SECRET`, run `recovery release`, restart and check health. Release advances independent authority. All accounts remain suspended; review before unsuspending. Keys, publications, contact, email preferences and intake require fresh choices. Take and verify a new backup.

Quarantine changes only the authenticated scratch target before replacement. It does not advance the external generation, so a crash during replacement can retry the same source safely; each retry again quarantines everything. The release and subsequent permission-restoring actions advance normally. Retain the previous reviewed application and a private pre-migration recovery plan until the first new backup succeeds.
